## Context

Removing Jazz took the store of record to SQLite (`2026-08-30-609b6c`) but left
collaboration without a transport: cojson carried changes between peers, and
nothing replaced it. Thirteen collaborative e2e tests have been red since.

cr-sqlite gives us the merge — every replicated table records `crsql_changes`
rows that any peer can apply in any order — so what was missing was only the
courier.

## Change

**Transport** (`electron/main/sync/`, shared by both modules):

- `wire.ts` — tags every value by SQLite storage class, so a BLOB primary key
  and a numeric string survive JSON intact, and 64-bit versions travel as
  strings.
- `protocol.ts` — three messages (`hello`, `want`, `changes`), and the recorded
  trust model: **the relay is trusted and sees plaintext**, a deliberate step
  down from Jazz's zero-knowledge relay.
- `relay.ts` — a WebSocket hub that stores nothing and forwards everything but
  `hello` to the rest of the room.
- `client.ts` — per-peer cursors in `crsql_tracked_peers`, never echoing a
  peer's own writes back, and applying each batch in one transaction.
- `relayMain.ts` — the relay as its own process, built as a second `main` entry
  (`dist/electron/main/sync-relay.js`).

**Wiring** (this change):

- `attachSync` / `detachSync` run inside `workspaceDb()` / `closeWorkspaceDb()`,
  so a peer syncs exactly the database that is open.
- The relay **room is the workspace `coId`**, not its local name — each peer
  names its own folder, and the join dialog offers a rename.
- Sharing decides *whether* to sync; `KLIPPEL_SYNC_URL` only overrides *where*.
  `enableJazzWorkspaceSync` calls `reattachSync(name)` **after** its
  close-and-reopen, which also opens the database — otherwise the peer that
  just shared sits offline, answering no joiner's catch-up.
- The relay tells a room when someone joins, and every member re-asks on that
  notice. Without it catch-up depended on connection order: a peer asks `want`
  once, and whoever connects later never hears the question.
- **CHECK constraints are suspended while merging** (`applyChanges`). A change
  row carries one column, so cr-sqlite materialises an incoming row from
  defaults and fills it in; `material_edges.type IN (…)` rejected that
  intermediate row, the whole batch failed, and the peers silently stopped
  converging. Checks still run in full on local writes.
- **`model_edit_leases` is now replicated.** A lease only the holder can see is
  not a lock. The objection — an offline holder locking a model forever — is
  answered by the TTL every reader already honours.
- Materials `afterWrite()` and every Composer model write, lease included, call
  `pushLocalChanges()`; remote batches raise `onRemoteChanges`, which the
  Materials main module turns into the same `notifyCatalogChanged()` tick a
  local write raises — the renderer needs no new path.
- The collaborative harness spawns the built relay **alongside** the cojson
  sync server, and passes each peer both URLs. Two servers on purpose: domain
  data replicates through the relay, but workspace identity is still Jazz's —
  a peer with no cojson server cannot join at all.
- **Sync attaches when a workspace opens** (`openWorkspaceJazzNodeInner`), not
  lazily on the first catalog read. A shared workspace that is merely open must
  already be receiving other people's changes; waiting for a read left a peer
  silently offline, answering nobody's catch-up.
- **A push carries only locally authored changes** (`changesSince` filters on
  `site_id`). Without that filter a peer that had just caught up echoed the
  whole merged history back on its next edit — measured at 193 898 rows re-sent
  after one edit on a 1 000-material workspace. Catch-up is the `want` path's
  job, and `changesFor` still answers with everything a peer holds.
- `getSyncStatus()` gained a `relay` block (room, url, site, connected, pushed,
  applied). "Is sync working" was otherwise unanswerable without reading logs,
  and the two failures above both presented as "nothing happens".

### Debug session

`Debug Two Peers (Collaborative, HMR)` runs both servers now: the new "Sync
Relay" configuration builds `electron/main/sync/relayMain.ts` from source with
esbuild on every launch (`scripts/devtools/sync-relay.mjs`, also `npm run
sync:relay`), so a session can never relay through a stale protocol. Peers get
`KLIPPEL_SYNC_URL=ws://127.0.0.1:4300`, and `two-peer-share.mjs` now ends by
asserting both peers report a connected relay in the same room with distinct
site ids — the step that caught the lazy-attach bug above.

The systray peers indicator shows the same relay block, so the question is
answerable from the running app as well.

## Status notes

All 14 collaborative e2e tests pass: 7 functional (Materials type/material
sync both directions, Composer join + cross-peer models + lease banner) and 6
performance, plus a new one pinning the relay-status contract the debug
session depends on. Convergence at 4 peers measured 235ms against a 20s
budget; propagation under churn, 5ms.

Verified by hand in the two-peer debug session as well: a material created on
A appeared on B in 1 785ms, and B's edit came back to A in 5ms, with A
applying 4 change rows rather than the 193 898 it echoed before the author
filter.

Still open: bootstrap-by-file-copy for a peer joining a large workspace
(replaying ~1.7M change rows at 100k materials is the wrong way to seed), and
`currentAccountId()`, which still reads Jazz.

## Security

The trust model changed and is worse: the relay sees every change in plaintext
and nothing stops it forging one, where cojson signed each change and relayed
only ciphertext. It follows that a relay must be run by whoever owns the data —
a public relay is not an option under this design. Peers authenticate with a
shared `KLIPPEL_SYNC_TOKEN`, taken from the environment rather than argv so it
is not visible to every process on the host; a peer presenting the wrong token
is closed (4401) rather than ignored, so a misconfiguration fails loudly. A
socket that has not said `hello` is in no room and cannot inject changes.
Recorded in full at the top of `protocol.ts`.

Suspending CHECK constraints while merging (above) means a peer's rows are not
validated by the engine on arrival. That is a real narrowing, and it is only
tolerable because this design already requires every peer and the relay to be
trusted; local writes are still fully checked.

## Performance

Pushes are event-driven, not polled: a write path calls `push()`, which selects
only changes newer than an in-memory cursor, so an idle peer does no work and a
change leaves the machine immediately. Applying a batch is one transaction.

Measured by the collaborative performance suite at 103 materials: convergence
235ms across 4 peers (budget 20 000ms), search under sustained churn 494–557ms
across 2–5 peers (budgets 3 000–4 000ms), propagation under churn 5ms.

The known cliff is a **fresh peer joining a populated workspace**: it asks for
everything from version 0, which at 100k materials is on the order of 1.7M
change rows over a WebSocket. That is why bootstrap-by-file-copy is listed as
open above rather than treated as a later optimisation.
