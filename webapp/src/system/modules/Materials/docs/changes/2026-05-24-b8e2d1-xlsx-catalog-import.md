## Context

The Materials module just removed both the renderer-side `.session/` cache ([jazz-only-storage doc](./2026-05-24-a1f3c7-materials-jazz-only-storage.md)) and the hardcoded `materialTypes` mock middleware. After those two cleanups, a freshly-bootstrapped workspace has an **empty** catalog — no materials, no types — and the only way to add data is the per-row Add form. That form is fine for a few entries but is not how the user is going to seed an existing inventory.

The bundled `public/materials/materials.xlsx` already exists; it was generated by [`scripts/generate-materials-fixture.mjs`](../../../../../scripts/generate-materials-fixture.mjs) from the legacy `mockedMaterials` literal. Today the fixture is **only** consumed during local development by manual import-via-devtools — there is no UI for it. This change wires that file (and any user-provided xlsx with the same schema) into the catalog through the existing Jazz IPC surface, and extends the workbook with a `MaterialTypes` sheet so types come in alongside materials.

Constraints:

- **Main-process parsing + writes.** Parsing a multi-thousand-row workbook plus the ensuing per-row CoValue writes would block the renderer thread for seconds. The renderer must stay interactive while the import runs — the user keeps browsing the (partial) catalog and clicking Atualizar. Run the whole xlsx → catalog pipeline in the main process; the renderer's only job is to read the file bytes, hand them over, and observe the catalog tick on `jazz-materials:changed`.
- **Async hand-off.** The renderer call returns as soon as the job is queued in main — not when the import finishes. The renderer gets a `{ jobId }` ack it can use to display "Importação em andamento…". Completion is delivered through a separate push channel (`materials:import-finished`) carrying the per-sheet summary the import UI surfaces.
- **No new Jazz mutators.** The importer calls the same `addMaterial` / `registerMaterialTypeVersion` functions in [`Materials/main/materials.ts`](../../main/materials.ts) that the renderer IPC handlers already invoke. No new write surface, no new validation path.
- **Idempotent re-import.** Re-importing the same file must not duplicate rows. The main-process importer pre-reads the current catalog (one `requireCatalog` call), computes a `Set<id>` per sheet, and skips rows already present. Reuse of the existing per-row duplicate-id rejection is the backstop.
- **Live updates over the existing channel.** Every successful `addMaterial` / `registerMaterialTypeVersion` already fires `onCatalogChange`, which the renderer turns into `loadMaterialsCatalog` (see [`Materials/kernelCalls.ts`](../../kernelCalls.ts) lines around 35-45). The import's only renderer-side effect is to dispatch *nothing* — rows arrive through the same tick that handles user-initiated edits. No bespoke streaming protocol.

## Change

What this change builds, top-down from the user-visible UI to the main-process pipeline:

### Renderer

- **`components/ImportCatalogSection.tsx`** — new ribbon section under the Materiais tab, between `EstoqueSection` and `TiposDeMateriaisSection`. One button "Importar xlsx" wrapped in a `PointerContainer`. The popup body has:
  - A hidden `<input type="file" accept=".xlsx,.xls">` triggered by an "Escolher arquivo" button.
  - A "Importar fixture" link/button that fetches `/materials/materials.xlsx` (the bundled file) as an `ArrayBuffer` and feeds it through the same submit path.
  - A status block, transitioning through three states:
    1. *idle* — file chooser visible, confirm disabled.
    2. *queued* — "Importação iniciada (job `abcd…`). Você pode continuar usando o app." Shows immediately after the IPC ack.
    3. *finished* — per-sheet summary: `N types added · M materials added · K skipped (already exist) · E errors`. Pulled from the `materials:import-finished` push event.
  - The container's first action is a `ConfirmAndCloseButton` labelled "Importar" — disabled until a file is selected; clicking calls `window.electron.jazz.materials.importXlsx(buffer)` and transitions to *queued*. The popup can be closed at any time without cancelling the job; if it's still open when `materials:import-finished` arrives, it flips to *finished*; if closed, a `Snackbar` in the same component (via a Layout-level toast manager if one exists, otherwise inline) shows the finished summary.
- **`hooks/useXlsxImport.ts`** — thin renderer-side wrapper. Reads `File → ArrayBuffer` (`file.arrayBuffer()`), calls the IPC, subscribes to `materials:import-finished` for the lifetime of the component (auto-unsub on unmount), exposes `status` + `summary`. No parsing logic in the renderer.
- **Ribbon wiring** — `kernelCalls.ts` registers `ImportarCatalogo` in `componentRegistryManager` and inserts it into the existing ribbon tab between the two existing sections. Optional `i` ribbon shortcut (with `ShortcutHint`, per repo `CLAUDE.md`); skip if it conflicts with anything already bound on that ribbon context.

### Preload + main IPC surface

- **`electron/preload/jazz.ts`** — extend `electron.jazz.materials` with:
  - `importXlsx(buffer: ArrayBuffer): Promise<{ jobId: string }>` — invokes `materials:import-xlsx` and returns as soon as the main process has queued the job.
  - `onImportFinished(listener: (payload: ImportFinishedEvent) => void): () => void` — wraps `ipcRenderer.on("materials:import-finished", …)` with an unsubscribe closure; same pattern as the existing `materials.onChanged`.
- **`electron/main/jazz-hooks.ts`** — register `ipcMain.handle("materials:import-xlsx", …)` that delegates to `runImportXlsx` (below) and returns the synchronous `{ jobId }`. Wire `onImportFinished` so completion events fan out to every active `webContents`.

### Main-process importer

- **`system/modules/Materials/main/importer/`** — new subfolder. Splitting it out keeps `main/materials.ts` (already ~900 lines) from absorbing the xlsx surface.
  - `index.ts` — exports `runImportXlsx(buffer: ArrayBuffer): { jobId: string }` (sync return) and `onImportFinished(listener)` (subscribe API mirroring `onCatalogChange`). The function schedules an `setImmediate(() => importer.run(buffer))` so the IPC handler returns before parsing starts. A single in-flight import is enforced (queue rejects a second call with a known error code while one is running); the user is unlikely to need parallel imports and concurrent CoValue writes from two parsers complicate the dedupe path.
  - `parser.ts` — pure functions, unit-testable, no Jazz / Electron deps:
    - `parseWorkbook(buffer)` → `{ types, materials, attributes, composition, caracteristics, suppliers, errors }`.
    - `parseMaterialTypesSheet(rows)` → `MaterialTypeVersionDTO[]`. Validates `name`, `version` (semver-ish), parses `attributesJson` + `selectorJson`. Constructs `id` as `${name}@${version}`.
    - `parseMaterialsSheet(rows)` → `MaterialDTO[]` keyed by id. Numeric coercion for `stockAmount`; `images` parsed from JSON; empty strings dropped.
    - `parseAttributesSheet(rows)` → `Record<materialId, AttributeMap>`. Respects the `kind` column (`object` rows are `JSON.parse`d, scalars stay as primitives).
    - `parseCompositionSheet`, `parseCaracteristicsSheet`, `parseSuppliersSheet` — same per-row join pattern.
    - `assembleAddMaterialInput({ material, attrs, composition, caracteristics, suppliers, typeVersion })` → the exact `AddMaterialInput` shape `addMaterial` in `main/materials.ts` already takes.
  - `runner.ts` — orchestration:
    1. Snapshot the current catalog via `requireCatalog` once.
    2. Compute skip-sets: type ids already present (`${name}@${version}`), material ids already present.
    3. For each new type: `await registerMaterialTypeVersion({ id, schemaJson, predecessorId })` from `main/materials.ts` directly (no IPC hop).
    4. For each new material in chunks of 25, with `await new Promise(r => setImmediate(r))` between chunks: `await addMaterial(input)`. Yielding to `setImmediate` lets pending IPC ticks (renderer Atualizar clicks, other windows' messages) interleave; cojson's sync manager also gets a chance to flush.
    5. Push `materials:import-finished` with the summary (`{ jobId, addedTypes, addedMaterials, skipped: { types, materials }, errors }`) once the loop completes — or on early abort with a top-level error.
- **Live updates piggy-back the existing channel.** Each `addMaterial` already pokes `onCatalogChange`, which fires `jazz-materials:changed`, which the renderer kernel call translates into `loadMaterialsCatalog`. The user sees the table fill in chunk by chunk; no new event for this.

### Fixture generator

- **`scripts/generate-materials-fixture.mjs`** — extend with a `MaterialTypes` sheet generated from the same legacy mock that previously lived in `materialTypes/middlewares.ts`. Columns: `name`, `label`, `version`, `attributesJson`, `selectorJson`. Re-run produces a new `public/materials/materials.xlsx` with one extra tab; the four existing sheets are untouched. ## Roadmap

**Phase 1 — Fixture + parser.** Fix the `i2mport.meta.url` typo, add the `MaterialTypes` sheet to the generator, regenerate `public/materials/materials.xlsx`. Land the pure `parser.ts` functions and unit tests against the regenerated fixture. Gate: `parseWorkbook(fixtureBuffer)` returns the same `{ types: N, materials: M }` counts the legacy mocks held.

**Phase 2 — Main-process runner + IPC.** Implement `runImportXlsx` + `runner.ts` with the chunked `setImmediate` yield loop, single-in-flight guard, and `materials:import-finished` push. Add the `materials:import-xlsx` IPC handler and preload bindings. Gate: a Node-side integration test (or a one-off harness script) drives `runImportXlsx(fixtureBuffer)` against an empty workspace, asserts post-run `loadMaterialsCatalog` returns the expected counts, and asserts re-running it is a no-op.

**Phase 3 — UI.** `ImportCatalogSection` with `PointerContainer`, file picker, fixture button, queued/finished status block. Subscribe to `materials:import-finished` for the summary. Wire into the ribbon. Gate: e2e click-driver runs the fixture path end-to-end — the popup transitions to *queued* immediately, the DataGrid fills in over the next few ticks via the existing `jazz-materials:changed` path, and the *finished* summary lands.

**Phase 4 — Deferred.**
- xlsx **export** of the live catalog (the natural inverse — keep the parser/serializer pair symmetric).
- Drag-and-drop onto the table view.
- Industry/supplier `OrgNode` import (today the main process auto-creates these from the raw string in `AddMaterialInput.material.industry` / `suppliers`).
- Cancellation / pause UI (the runner has a single in-flight guard but no cancel token yet).

Open follow-ups carried over:

- **Should we add a `MaterialTypes` sheet, or a separate workbook?** Single workbook is simpler for the user (one drop), and types-before-materials ordering is enforced by the importer regardless of sheet position. Going with single workbook unless it makes round-tripping awkward.
- **Per-attribute CoValues on bulk import.** Each material's attributes are written through the existing `addMaterial` IPC, which today does a wholesale `attributes` record set rather than per-cell diff (called out in the parent doc as "remaining Phase 3 work"). Bulk import will therefore *create* per-attribute CoValues for new rows (correct) but cannot demonstrate the conflict-free merge advantage until that diffing lands. Not a blocker.
- **Failure mode for malformed rows.** Three options: (a) abort the whole import on first error, (b) skip the row and keep going, (c) abort the sheet but keep prior sheets. Going with (b) plus a per-row error list in the summary — partial success is more useful than nothing for a 200-row file with two bad rows.

## Security

- **Untrusted input crosses the IPC boundary.** Renderer hands the xlsx contents to main as an `ArrayBuffer`. The main-process importer must:
  - Cap workbook size (target: reject > 20 MB before parsing; `xlsx` will happily try to parse much larger files and exhaust main-process memory). The renderer should pre-check `file.size` for a friendly error, but main is the authoritative gate.
  - Cap row counts per sheet (target: 50k materials, 200k attribute rows). Over-limit workbooks fail the whole job with a `payload_too_large` error in `materials:import-finished`, no partial writes.
  - `JSON.parse` every JSON-typed cell inside a `try`/`catch` and surface the row as a `skipped` entry; never let a parse exception take down the import loop.
  - Treat string attribute values exactly as the existing Add form path does — they go through `addMaterial`'s existing validation; no new sanitization step is introduced here.
- **One new IPC surface.** `materials:import-xlsx` is the only new write channel. It is gated by the same single-account-per-process model the rest of `electron.jazz.materials.*` uses; no auth changes.
- **Single in-flight job.** A second `importXlsx` call while one is running rejects with `import_in_flight`. Without this guard, two parsers racing on the same `requireCatalog` snapshot would both compute their skip-sets as "id X not present", then both call `addMaterial(X)` and one would fail noisily on the existing duplicate-id rejection. Cheaper to refuse.
- **Bundled fixture path.** `/materials/materials.xlsx` is served from `public/`. The renderer fetches it via `fetch()` and re-uploads the bytes through the same IPC — no special "import the bundled file" handler on main, so there's only one parsing path to harden.
- **`materials:import-finished` push fan-out.** The main-side `onImportFinished` registration must clean up on `webContents.destroyed` (same pattern as `materials:subscribe`) so renderer reloads don't leak listeners.
- No new credential or secret handling.

## Performance

- **Renderer thread stays responsive.** Parsing + the per-row write loop runs in the main process; the renderer pays only the cost of reading the file into an `ArrayBuffer`, transferring it across IPC, and re-rendering the DataGrid as `jazz-materials:changed` ticks land. A 1k-row import is invisible from the renderer's frame budget.
- **Main-process memory.** Parsed in-memory representation of the bundled fixture is ~50 KB (18 materials, ~150 attribute rows). The 50k-material cap corresponds to ~30–40 MB peak in main during parse; acceptable for a one-shot import, but the file-size cap is what prevents pathological inputs.
- **Write loop pacing.** Chunked at 25 rows with `setImmediate` between chunks means a 1k-row import takes ~40 ticks of the main event loop. `setImmediate` (vs `setTimeout(0)`) is the right primitive in main — it preserves cojson sync flushes and keeps IPC responsive without the 1 ms minimum-delay clamp.
- **Live updates.** Renderer sees ~40 `jazz-materials:changed` ticks during a 1k-row import (one per chunk-boundary CoValue write batch). Each tick triggers a single `loadMaterialsCatalog` IPC call that reads the catalog and replaces the slice. To avoid that becoming O(n²) on really big imports we may need to debounce the change event in main (already a possibility flagged elsewhere); for the 1k–50k range that change doc targets, the cost is acceptable. Add a debounce only if profiling shows tail latency regress.
- **No CoValue compaction needed.** The catalog is per-CoValue today (parent doc), so a 1k-row import creates ~3k CoValues (material + attributes record + stock). Within the budget the parent doc set; revisit only if catalog load cost regresses.
- **No benchmark in this change.** Add a `bench` script later if catalog cold-load time crosses a noticeable threshold (e.g. > 500 ms on the dev machine for a 1k-row catalog).
